1. 功能描述

Story 功能描述
WhyUB 端口或路径故障后，业务可能通过 TCP payload 或持续 retry 表现为成功率下降，而不是明确失败。目标是避免静默故障：故障 worker 恢复前不再继续写入数据或迁移数据，读取命中故障数据 worker 时快速返回可识别错误。

本页的结论以 CodeGraph 命中的当前源码为准：Client Put 的 UB write 在 client 发起；Worker/Client RemoteGet 请求里的 UB write 在数据 provider worker 端发起；Rebalance/Migrate 是 worker-worker RPC 后的数据迁移。本文只聚焦 UB 故障隔离，不展开 worker 故障自愈。

1.2 功能目标与边界

准入条件

所有写入和迁移目标都通过同一个组合判断：WorkerServiceMode(worker) == RUNNING 且 WorkerUbPathHealth(worker) == AVAILABLE。任一不满足，默认 fail fast。

最小修改原则

不新建复杂的数据面健康中心；新增轻量的 UB 路径观测缓存和准入接口，挂到现有 client put、worker provider write、remote get、migration/rebalance 入口。

隔离含义

这里的隔离不是把节点从集群摘除，而是对“向某 Worker 发生 UB 写入/迁移”的数据面准入关闸。读请求命中故障数据所在 Worker 时快速返回可识别错误。

非目标边界

UB 隔离只处理数据面路径 eligibility；服务级网络断链、节点自愈、元数据/slot/ownership 恢复仍由现有机制处理，不在本文展开。

1.3 关键概念定义

1.3.1 全局事实与局部观测

Global Fact

由 master/etcd/hash ring/cluster metadata 维护的全局事实，例如 Worker 是否在 ring 中、slot 归属、primary copy、迁移任务状态。

Local Observation

由单个 client 或 worker 发起 URMA 单边操作时获得的局部观测。ERROR 4 是 UB 端口不可用的确定信号；CQE error、wait timeout、Jetty async event 需要按类型分类。

Admission Result

请求入口对两类信息做组合判断，但局部观测不能直接改写全局事实；最多阻止本进程继续写入，并通过 RPC/错误码把对端 UB 故障传出去。

1.3.2 Meta/Layout 与 Data Local

Meta/Layout对象位置、primary、slot、迁移任务。
Data Local某 Worker 本地内存/共享内存/SSD 中真实数据。
Worker Provider持有 object data 并被要求把数据写到 requester 的 worker。
Requester发起读写/迁移请求的一端，可能是 client 或 worker。
TransportURMA/UCP/TCP 的实际数据传输路径。

设计要避免把 transport 层“某一跳不通”误解释为对象不存在或元数据错误。新增错误语义建议为 K_OC_DATA_PROVIDER_UB_UNAVAILABLE 或同类 URMA data-plane code，表达“数据在该 Worker，但该 Worker 的 UB 路径暂不可用”。

3. 方案详细设计

3.0 关键问题回答

发起端如何感知目的端 Worker UB 故障

client->worker Put/Set 是 client 自己发起 UrmaWritePayload，因此 client 能直接拿到 ERROR 4、CQE error、wait timeout 等 operator 结果。ERROR 4 是目标 worker UB port 不可用的确定信号，立即把该 worker 写入本地 PeerUbAdmission 的 UNAVAILABLE；ERROR 9 先按可恢复 Jetty/CQE 错误进入 SUSPECT/PROBING，连续失败或 probe 失败后再隔离。

RemoteGet 触发 UB Write 时如何归因

RemoteGet 的 requester 只是发 RPC，真正的 UB Write 发起端是数据 provider worker。provider 在 WriteViaFastTransport 或 UbWriteHelper 里看到真实 URMA 结果后，必须把结构化状态放回 RPC response：failed_endpoint、failure_side、urma_status、operator_worker。requester 只有收到这个显式状态，才能更新本地 admission；RPC timeout/failure 只标记 peer suspect，不能合成 ERROR 4。

后续如何感知 UB 恢复

恢复不依赖业务请求试错。被隔离 peer 进入 cooldown，之后由 UbRecoveryProbe 做 handshake / warmup / small URMA probe；probe 成功 N 次或收到带更高 epoch 的全局健康摘要后，状态从 UNAVAILABLE 转为 PROBING 再到 AVAILABLE。fallback 成功不能恢复 UB health。

目的端 Worker 如何知道自己故障并通知别人

被单边写的一端不能天然看到对端写失败，所以目的端 worker 需要两类输入：本地自检看到 ERROR 4/频繁 ERROR 9/Jetty 重建后 probe 失败；以及其他 client/worker 通过 RPC 上报“写不进该 worker”。worker 聚合这些信号更新 LocalUbHealth，再通过 master heartbeat 的 extend 或 client-worker heartbeat response 带出 UbHealthSummary，让其他节点减少向它写入和迁移。

结论：第一层必须是发起端局部感知和本地准入，保证 Put/Get/RemoteGet/migrate/rebalance 立即止血；第二层才是轻量全局摘要和保活探测，用于恢复和减少其他节点继续撞同一故障 Worker。持续故障必须指数退避，避免 probe 或重试流量放大。

3.1 现状分析

当前代码已经有明确的 UB 失败观测点，但观测分散在 client 写、provider 写回、direct read transport、migration/rebalance 目标选择等路径。风险不是“完全没有错误码”，而是错误没有形成统一的下一次准入决策，导致 fallback、retry 或 batch 内重复请求继续撞同一条坏 UB 路径。

构建单元与职责拆分

发起端：Requester / URMA Writer

发起 URMA 单边操作的一端拥有最可靠的失败观测。它负责形成 UbOpOutcome、调用 UbFailureClassifier 分类，并通过 WorkerUbPathHealth 更新本地 health。

Worker Provider

只有 Worker 提供 object data，并常常根据 RPC 里的 URMA info 写回对端。URMA Write 的真实 completion/error 只在 Worker Provider 侧出现；Provider 失败后要把“对端 UB 不可写”的显式 URMA 状态反馈给 requester，避免 requester 只能靠 RPC 超时猜测。

服务级状态

WorkerServiceMode 只作为已有服务态输入。本文不设计 worker 自愈，只要求 UB admission 不把局部 UB 观测改写为全局 worker DOWN。

数据面准入

TransportPathAdmission 是最小公共入口，client put、worker remote get、migration/rebalance 都只问它“这个源/目标现在能否走 UB 写”。

命名建议：不要用过重的 DataPlaneHealthManager 语义。更贴切的是 WorkerUbPathHealth + TransportPathAdmission：前者记录局部观测和恢复状态，后者做组合准入。

3.2.2 部署

部署形态

不新增进程，不改变 SDK 对外 API；新增逻辑随 client/worker 进程内 object-cache transport adapter 加载。

默认策略

UB fallback 默认关闭；显式开启时仅允许 <= 1MB 的普通读写 fallback，不覆盖 migration / rebalance。

3.2.3 运行

运行期最小修改点

新增轻量模块

WorkerUbPathHealth：进程内 peer -> health 状态，保存原因、时间、epoch、cooldown、probe 状态。

新增准入接口

TransportPathAdmission：给 put/get/migrate/rebalance 调用，组合服务态、UB 观测、fallback 策略。

新增局部/全局桥接

LocalUbHealth 表示本 worker 自己 UB 数据面是否可写；UbHealthGossip 只通过已有心跳传播摘要，不直接触发 worker 下线。

新增错误码

新增或复用 URMA error 家族，表达“数据所在 Worker UB 不可用”与“目标 Worker UB 接收不可用”。

新增恢复 probe

先 cool-down，再 small probe。连续失败按 1s/2s/4s/8s/10s 退避；probe 成功只恢复该 peer 的 UB path，不改全局 membership。

运行路径接入点

  • Client在 SendBufferViaUb* 前检查目标；失败后标记目标 UB path unavailable，并返回显式错误。
  • Provider Worker在 WriteViaFastTransport 失败后标记 requester UB path，并把显式 URMA operator status 放进 response。
  • Requester Worker在 PullObjectDataFromRemoteWorker 收到显式 UB unavailable 时快速失败或换副本；若只是 RPC timeout/failure，则按 provider/RPC suspect 处理，不当成对象缺失或本端 ERROR 4。
  • Migration在 ConnectAndCreateRemoteApi 或更上层目标选择前检查 migration target。
  • Heartbeatworker 把本地 UB health epoch/reason/backoff 放进 master heartbeat extend 或 client-worker heartbeat response；接收方只更新 peer admission，不修改 membership。
  • Fallback默认关闭；开启时仅允许小于等于 1MB 且非迁移路径的读取/写回，且要打点记录。

场景风险补充处理
Client direct read batch按 data worker 分组后，一个坏 data worker 可能让 batch 内多个对象重复等待。分组后发 batch 前调用 CheckReadSource，整组 fail fast 或换副本。
传统 Client Get provider 写回 clientUB Write 失败只在 worker provider 看到，client 只看到 RPC 结果。provider 返回结构化 URMA status，client 只消费显式状态；RPC timeout 不合成 ERROR 4。
Worker remote get / BatchGetObjectRemoterequester 可能持续读同一个 provider，provider 也可能持续写不进 requester。requester 对 provider 做 source admission；provider 对 receiver 做 endpoint admission，并在 response 携带 failed endpoint。
Migrate / Move / Rebalance扩缩容或故障期间 stale task 仍把数据迁移到 UB 不可写 worker。目标选择和执行前都查 CheckMigrationTarget；scale-up 新 worker 初始为 PROBING，scale-down/exiting worker 直接拒绝。
持续 ERROR 9Jetty 重建可恢复，但频繁重建会把真实业务流量变成 probe。ERROR 9 先触发 ReCreateJetty 和 SUSPECT，窗口内超过阈值后进入 UNAVAILABLE 并指数退避 probe。
全局恢复只有本地隔离会导致不同 client/worker 恢复时间不一致。心跳摘要携带 epoch，新 epoch + probe success 才恢复本地 admission；摘要只能加速恢复，不能替代本地 probe。

3.2.4 元戎整体如何使用

  • 业务使用方式不变；UB 故障隔离作为 client/worker 内部准入和错误返回能力生效。
  • client->worker 写入失败后，恢复前同一 target worker 的写入快速失败。
  • RemoteGet 路径由 requester 先过滤 data source，provider 在处理请求时上报显式 UB Write 失败。
  • migration/rebalance 只把 UB health 当作 target eligibility 输入，不改变 metadata ownership。
  • 扩容 worker 在 UB probe 成功前不承接 UB 写入/迁移；缩容或故障 worker 在 service/ring 已不可写时直接拒绝作为 target。
  • 心跳摘要用于传播“本 worker UB 数据面是否可写”，但不把局部 UB 故障升级为 worker DOWN。

3.2.6 高性能设计 topic

  • 准入判断必须是进程内 O(1) 读本地状态，不能在普通 Put/Get/RemoteGet 关键路径上同步访问外部服务。
  • 失败后同一 worker/source 的 batch remote get 要按 worker 分组 fail fast，避免 batch 内每个对象重复等待超时。
  • 恢复 probe 不能借真实业务请求试错；cooldown 后用小数据 handshake/warmup/probe，成功后再放开业务流量。
  • 持续故障按指数退避控制 probe 和重试频率，避免所有 client/worker 同时把故障 worker 打满。
  • fallback 默认关闭；即使开启，也只对小对象生效，并且 fallback 成功不清除 UB health。

4.2 待确认策略

  • 错误码命名：建议放在 OC/URMA 交界处，保留 provider UB unavailable 与 requester UB unavailable 两类语义。
  • 恢复 probe 的实现：优先复用现有 handshake / warmup / small URMA write；心跳只传播摘要和 epoch，不承担数据面 probe。
  • fallback 策略：默认关闭；开启时建议只覆盖 <= 1MB 普通读写，不覆盖迁移和 bulk rebalance。
  • 局部观测传播范围：第一阶段用 RPC response + heartbeat summary 做轻量传播；master 只保存摘要，不参与普通 Put/Get 同步准入。
一句话版本：本文只回答“现在能不能往这个 Worker 的 UB 数据面写”。已有 worker membership/rpc health 可以作为输入，但不是本文设计对象。
