1. Story 整体设计

1.1 功能描述

UB 端口或路径故障后，业务可能表现为成功率下降、批量请求局部超时、迁移任务反复失败，而不是明确告诉调用方“数据所在 Worker 的 UB 数据面不可用”。本需求的核心目标是避免静默故障：故障 Worker 恢复前不再继续写入数据或迁移数据，读取命中故障数据 Worker 时快速返回可识别错误。

5W1H 说明
  • Who：Client、发起 RemoteGet 的 Worker、提供数据的 Worker、迁移/Rebalance 执行方；开发和测试都要区分“请求发起端”和“真正发起 UB Write 的一端”。
  • What：URMA Write 链路或 Worker UB 能力异常时，停止继续通过异常 UB 路径写入/迁移；读命中受影响 Worker 时快速失败或换源。
  • When：URMA Write 发起端返回 ERROR 4、连续 ERROR 9/timeout、provider 显式返回 UB 写失败、probe 未恢复或健康摘要显示不可写时触发。
  • Where：Client 写入路径、Client/Worker RemoteGet 路径、Direct Read data phase、Migrate/Rebalance target 选择与执行前。
  • Why：避免 UB 故障被 retry、fallback 或 batch 局部失败掩盖，造成持续静默成功率下降。
  • How：通过本地准入、显式错误返回、轻量健康摘要、probe 恢复和指数退避实现；DryRun Cases 展开可注入流程和变化模块。
影响范围

Client 写入、Client 读取、Worker 远端读取、批量远端读取、数据迁移、Move/Rebalance 都可能被 UB 静默故障影响。

故障表现

调用方需要看到明确错误，而不是成功率下降、长时间等待、批量请求局部静默失败，或迁移任务持续重试同一个异常 Worker。

用户体验

故障后返回明确错误并 fail fast，避免继续撞同一个坏 Worker；恢复由 probe 与健康 epoch 平稳放开，不靠真实业务请求反复试错。

边界

UB 隔离只处理数据面 eligibility，不把局部 UB 故障直接升级成 Worker 全局 DOWN；membership、slot、primary、迁移任务仍由 Global Fact 维护。

功能目标与边界

成功标准

UB 故障后，后续写入、迁移、rebalance 不再继续打到同一个不可写 Worker；读命中故障数据 Worker 时快速返回可识别错误。

恢复标准

故障 Worker 只有在 UB 数据面恢复被确认后，才重新承接写入和迁移；恢复过程不能依赖普通业务请求反复试错。

隔离含义

这里的隔离不是把节点从集群摘除，而是关闭“向该 Worker 写入或迁移数据”的数据面通路；对象是否存在、primary 属于谁仍以全局元数据为准。

非目标边界

UB 隔离只处理数据面路径 eligibility；服务级网络断链、节点自愈、元数据/slot/ownership 恢复仍由现有机制处理，不在本文展开。

1.2 术语说明

全局事实与局部观测

Global Fact

由 Coordinator/etcd/hash ring/cluster metadata 维护的全局事实，例如 Worker 是否在 ring 中、slot 归属、primary copy、迁移任务状态。

Local Observation

由单个 client 或 worker 发起 URMA 单边操作时获得的局部观测。ERROR 4 是“本 URMA Write 发起端本地 UB 链路不可用”的确定信号；ERROR 9 表示 timeout，可能由对端、链路、调度等多因触发。DataSystem 在 ERROR 9 之后执行 Jetty 重建，再按重建/probe 结果进入 suspect/probe 或升级隔离。

Admission Result

请求入口对两类信息做组合判断，但局部观测不能直接改写全局事实；最多阻止本进程继续写入，并通过 RPC/错误码把对端 UB 故障传出去。

Meta/Layout 与 Data Local

Meta/Layout对象位置、primary、slot、迁移任务。
Data Local某 Worker 本地内存/共享内存/SSD 中真实数据。
Worker Provider持有 object data 并被要求把数据写到 requester 的 worker。
Requester发起读写/迁移请求的一端，可能是 client 或 worker。
TransportURMA/UCP/TCP 的实际数据传输路径。

设计要避免把 transport 层“某一跳不通”误解释为对象不存在或元数据错误。错误语义建议为 K_OC_DATA_PROVIDER_UB_UNAVAILABLE 或同类 URMA data-plane code，表达“数据在该 Worker，但该 Worker 的 UB 路径暂不可用”。

2.1 UC-1 Client 写 Worker：本端发起 UB 写失败

场景拆解
  • 最简单 case：Client Put/Set 写入 Worker A，Client 自己发起的 UB Write 返回 ERROR 4，或连续出现 ERROR 9/timeout。
  • AS IS：本次写请求失败后，后续请求仍可能继续使用 Client 自身异常 UB 发送链路；fallback、retry 或 batch 内部分失败会掩盖根因，业务侧只看到成功率下降。
  • TO BE：Client 把“本地 UB 发送能力异常”和受影响目标写入本地准入，恢复前后续 UB 写入快速失败；默认不透明切 TCP，只有显式开启且小于 1MB 的场景才允许走 TCP fallback。
  • 风险：继续通过异常本地 UB 链路写入会制造更多失败对象或部分成功状态；如果直接把 Worker A 标成全局 DOWN，又会误伤其他节点对 Worker A 的正常访问。
  • 最小判断：1 Client 是本次 URMA Write 发起端；2 ERROR 4 明确表示 Client 本地 UB 链路异常；3 ERROR 9 是 timeout，DataSystem 随后执行 Jetty 重建；4 本地 probe 尚未恢复前，后续写入不再进入真实 UB Write。

2.2 UC-2 Client Get 由 Worker 写回：Provider 写 Client 失败

场景拆解
  • 最简单 case：Client Get 命中远端 Worker B 上的数据，Client 通过 RPC 请求 Worker B 写回 Client receive buffer，Worker B 作为 URMA Write 发起端返回 ERROR 4。
  • AS IS：Client 可能只看到 Get RPC timeout 或读取失败，无法稳定区分对象不存在、Worker B RPC 不通、Worker B 写回失败，或 Client receive endpoint 不可写。
  • TO BE：Worker B 在 RPC response 中返回明确的 UB 写回失败状态，带出 failed endpoint、URMA 状态码和 operator worker；Client 消费显式状态后快速失败或按策略换源。
  • 风险：把写回失败当成对象不存在，会触发错误恢复；把 RPC timeout 合成 ERROR 4，会把弱网络信号误升级成 UB 硬故障。
  • 最小判断：1 Client 是 requester；2 数据所在 Worker 是 URMA Write 发起端；3 ERROR 4 归因到 Worker B 的本地 UB 写回链路；4 只有显式 URMA status 才更新 Client 对该 source 的判断；5 RPC timeout 只按 RPC/peer suspect 处理。

2.3 UC-3 Client Direct Read / Batch Direct Read：按数据 Worker 分组止血

场景拆解
  • 最简单 case：Batch Direct Read 里多个 object 的 data location 都是 Worker B，而 Worker B 的 UB 写回路径已经被本地准入或健康摘要判定不可用。
  • AS IS：Batch 内对象可能逐个发请求、逐个等待 timeout，导致一次 UB 故障被放大成 N 次超时和 N 次重试。
  • TO BE：Direct Read data phase 前按 data worker 分组检查 source/receiver 准入；同一故障 Worker 上的一组 object 整组快速失败或换可用副本。
  • 风险：逐对象撞同一个故障 Worker 会放大延迟和重试流量；batch 局部失败还会掩盖“同一 data worker UB 不可用”的根因。
  • 最小判断：1 获取到 object -> data worker location；2 按 data worker 分组；3 组级准入命中 unavailable；4 同组对象不再逐个进入真实 RemoteGet/UB 写回。

2.4 UC-4 Worker RemoteGet：Provider 写请求 Worker 失败

场景拆解
  • 最简单 case：Worker A 发起 RemoteGet，请 Worker B 把对象数据 UB 写回 Worker A，Worker B 作为 URMA Write 发起端返回 ERROR 4。
  • AS IS：Worker A 容易只看到 RPC timeout 或 RemoteGet 失败，并误判成本端 UB ERROR 4、对象不存在，或 Worker B 整体不可用。
  • TO BE：Worker B 作为 provider 显式返回 UB 写回失败；Worker A 只有在收到结构化 URMA status 后，才更新本地 admission 或触发换源。
  • 风险：Worker-worker 读路径如果误归因，会影响后续迁移、恢复、读取调度，甚至把 RPC 抖动升级成错误隔离。
  • 最小判断：1 Worker A 是 requester；2 Worker B 是数据 provider 和 URMA Write 发起端；3 ERROR 4 表达 Worker B 本地 UB 写回链路异常；4 显式 URMA status 与 RPC timeout 分支分离；5 requester 不把 timeout 合成 ERROR 4。

2.5 UC-5 Migrate / Move / Rebalance：目标 Worker 准入

场景拆解
  • 最简单 case：Migrate/Move/Rebalance 任务选择 Worker T 作为目标，但 Worker T 当前 UB 接收不可用，源 Worker 或迁移执行方写入 Worker T 失败。
  • AS IS：迁移任务可能只依据任务分配和元数据目标继续执行，反复连接同一个不可写目标，最终表现为迁移超时、迁移失败或 rebalance 进度停滞。
  • TO BE：迁移发送数据前检查目标 Worker 是否可接收 UB 写；不可写时拒绝目标，任务失败或重选目标，不向该 Worker 继续搬数据。
  • 风险：把数据迁到无法接收 UB 写的 Worker，会放大迁移失败并影响后续读取；持续重试还会占用 worker-worker RPC 和数据面资源。
  • 最小判断：1 迁移任务给出 target Worker；2 target 当前不可接收 UB 写、正在退出或尚未通过恢复验证；3 migrated bytes 保持为 0；4 任务记录 target rejected 或进入重选。

2.6 UC-6 扩容 / 缩容 / 故障恢复：GlobalFact 与 UB 准入同时满足

场景拆解
  • 最简单 case：Worker A 刚扩容加入 membership，或正在缩容/退出，或 UB 从故障中恢复，但本地 probe 尚未确认可写。
  • AS IS：服务态、ring 视图和 UB 数据面恢复状态可能不同步，节点一进入 membership 就过早承接写入/迁移，或恢复依赖真实业务请求试错。
  • TO BE：写入/迁移必须同时满足 GlobalFact 允许和 UB 准入可写；扩容先 PROBING，缩容/退出直接拒绝作为 target，故障恢复后 probe 成功才放开。
  • 风险：过早开放会把新写入和迁移派到尚不可写节点；过晚开放会浪费容量；把 UB 可用反向改写 membership 会破坏元数据权威边界。
  • 最小判断：1 GlobalFact 显示 worker 是否可作为 source/target；2 UB admission 是否 AVAILABLE；3 任一侧不可写则拒绝写入/迁移；4 恢复必须经过 probe/epoch 证据。

2.7 UC-7 目的端 Worker 自身 UB 故障：摘要传播减少撞击

场景拆解
  • 最简单 case：Worker A 自己作为 URMA Write 发起端时持续看到 ERROR 4，或 ERROR 9 timeout 后 DataSystem Jetty 重建/probe 失败，或收到多端反馈写回失败。
  • AS IS：被单边写的一端不天然知道每次对端写失败；如果只靠各个发起端局部隔离，其他 Client/Worker 仍会继续向 Worker A 写入或迁移。
  • TO BE：Worker A 聚合本地 UB 异常和 peer feedback，生成只描述自身的健康摘要，通过 heartbeat/response 让相关节点更新本地准入，减少继续写入和迁移流量。
  • 风险：千级节点下如果传播所有 peer matrix，会造成 O(N²) 心跳负担；如果完全不传播自身摘要，故障节点会被不同发起端反复撞击。
  • 最小判断：1 Worker A 只上报自身 UB health、epoch、reason、backoff；2 Coordinator/etcd 只保存 worker -> latest summary；3 消费方按相关候选 source/target 更新本地 admission；4 摘要不改写 membership。

3. 方案详细设计

3.1 现状分析

当前问题不是 UB 路径完全没有错误，而是错误归因分散：client 本端写、provider 写回、RemoteGet RPC、迁移/rebalance 目标选择都可能各自看到局部失败，却没有统一转化成下一次请求的准入决策。因此故障会表现为成功率下降、batch 局部超时或迁移反复失败。

方案一句话：针对 UB 故障静默失败隔离，数据发起端和数据接收端都增强对 URMA Write 结果、RPC 显式状态和本地 UB 能力的感知；为了性能，只通过全局通道传递“某个 Worker 的 UB 能力是否存在问题”的轻量事件，普通读写仍走本地准入。

方案的核心不是把 UB 故障升级成 worker 全局故障，而是在每个发起请求的 client/worker 本地建立数据面准入：不通就快速失败，恢复前不继续写入或迁移；恢复必须由 probe 或健康 epoch 证据确认，不能靠业务请求反复试错。

3.2 方案设计

发起 URMA Write 的一端如何归因

client->worker Put/Set 是 client 自己发起 UrmaWritePayload，因此 client 能直接拿到 operator 结果。ERROR 4 明确表示 client 本地 UB 发送链路有问题；ERROR 9 表示 timeout，可能由对端、链路或调度等多因触发。DataSystem 在 ERROR 9 之后做 Jetty 重建，随后进入 SUSPECT/PROBING，连续失败或 probe 失败后再隔离。

RemoteGet 触发 UB Write 时如何归因

RemoteGet 的 requester 只是发 RPC，真正的 UB Write 发起端是数据 provider worker。provider 在 WriteViaFastTransport 或 UbWriteHelper 里看到真实 URMA 结果后，必须把结构化状态放回 RPC response：failed_endpoint、failure_side、urma_status、operator_worker。Requester 收到显式 ERROR 4 时，归因为 provider 本地 UB 写回链路异常；RPC timeout/failure 只标记 peer suspect，不能合成 ERROR 4。

后续如何感知 UB 恢复

恢复不依赖业务请求试错。被隔离的本地 UB 能力或 peer path 进入 cooldown，之后由 UbRecoveryProbe 做 handshake / warmup / small URMA probe；probe 成功 N 次或收到带更高 epoch 的全局健康事件后，状态从 UNAVAILABLE 转为 PROBING 再到 AVAILABLE。fallback 成功不能恢复 UB health。

目的端 Worker 如何知道自己故障并通知别人

被单边写的一端不能天然看到对端写失败，所以数据接收端需要通过 RPC response、peer feedback 和全局 UB 能力事件补齐感知。Worker 自己作为 URMA Write 发起端时若看到 ERROR 4，或 ERROR 9 timeout 后 DataSystem 的 Jetty 重建/probe 仍失败，就更新 LocalUbHealth，再通过 Coordinator/etcd 元数据更新或 client-worker heartbeat response 带出 UbHealthSummary，让其他节点减少 RemoteGet、写入和迁移流量。

千级节点下心跳是否可行

可行边界是“每个 worker 只上报自己的 UB 摘要”，而不是在心跳里广播所有 peer 状态。Coordinator/etcd 侧维护 O(N) 的 worker -> health epoch 摘要；client/worker 只按当前连接、候选 data location、迁移 target 消费相关摘要，普通 Put/Get 仍走本地 O(1) admission。

3.2.5 运行接入与性能约束

最小改动点

不引入新进程

不改变 SDK 对外 API；相关逻辑随 client/worker 进程内 object-cache transport adapter 加载。

默认策略

UB fallback 默认关闭；显式开启时仅允许 <= 1MB 的普通读写 fallback，不覆盖 migration / rebalance。

运行期最小修改点

轻量模块

WorkerUbPathHealth：进程内 peer -> health 状态，保存原因、时间、epoch、cooldown、probe 状态。

准入接口

TransportPathAdmission：给 put/get/migrate/rebalance 调用，组合服务态、UB 观测、fallback 策略。

局部/全局桥接

LocalUbHealth 表示本 worker 自己 UB 数据面是否可写；UbHealthGossip 只通过已有心跳传播摘要，不直接触发 worker 下线。

错误码扩展

扩展或复用 URMA error 家族，表达“数据所在 Worker UB 不可用”与“目标 Worker UB 接收不可用”。

恢复 probe

先 cool-down，再 small probe。连续失败按 1s/2s/4s/8s/10s 退避；probe 成功只恢复该 peer 的 UB path，不改全局 membership。

运行路径接入点

  • Client在本端 UB 写入前检查目标；失败后标记目标 UB path unavailable，并返回显式错误。
  • Provider Worker在写回 requester/client 失败后标记对端 UB path，并把显式 URMA operator status 放进 response。
  • Requester Worker在收到显式 UB unavailable 时快速失败或换副本；若只是 RPC timeout/failure，则按 provider/RPC suspect 处理，不当成对象缺失或本端 ERROR 4。
  • Migration在目标选择和执行前检查 migration target，避免 stale task 继续向 UB 不可写 Worker 迁移。
  • Heartbeatworker 把本地 UB health epoch/reason/backoff 放进 Coordinator/etcd 元数据更新或 client-worker heartbeat response；接收方只更新 peer admission，不修改 membership。
  • Fallback默认关闭；开启时仅允许小于等于 1MB 且非迁移路径的读取/写回，且要打点记录。

千级节点下的心跳可行性

不做全量 all-to-all 心跳

千级节点下不能让每个 client/worker 在心跳中携带所有 peer 的 UB 状态，否则会变成 O(N²) 数据和广播放大。UB health 的全局通道只传播“本 worker 自己”的摘要：state、epoch、reason、backoff_until。

Global Fact 与 UB 摘要分层

Global Fact 仍由 Coordinator/etcd/hash ring 维护，解决 Worker 是否存在、是否 RUNNING、slot/primary/任务归属。UB 摘要只表示该 Worker 数据面是否适合作为写入或迁移目标，不替代 membership。

按需消费

普通 Put/Get 不同步访问 Coordinator/etcd；它只读本进程 O(1) 的 PeerUbAdmission。心跳摘要用于刷新本地缓存，RPC response 用于本次请求的精确归因，probe 用于恢复确认。

流量控制

持续故障时，probe 和重新开放按指数退避；Coordinator/etcd 侧只保存每个 worker 最新 epoch 摘要，client/worker 可只接收与当前连接、候选 location、迁移 target 相关的摘要。

  • 准入判断必须是进程内 O(1) 读本地状态，不能在普通 Put/Get/RemoteGet 关键路径上同步访问外部服务。
  • 失败后同一 worker/source 的 batch remote get 要按 worker 分组 fail fast，避免 batch 内每个对象重复等待超时。
  • 恢复 probe 不能借真实业务请求试错；cooldown 后用小数据 handshake/warmup/probe，成功后再放开业务流量。
  • 持续故障按指数退避控制 probe 和重试频率，避免所有 client/worker 同时把故障 worker 打满。
  • fallback 默认关闭；即使开启，也只对小对象生效，并且 fallback 成功不清除 UB health。

5. 约束

  • 不能把局部 UB 故障直接升级为 worker DOWN，也不能改写 object ownership / hash ring / migration task 的全局事实。
  • 普通 Put/Get/RemoteGet 关键路径不能同步访问 Coordinator/etcd；准入判断必须是进程内 O(1) 本地状态读取。
  • 千级节点下不能传播 peer matrix；心跳只传播本 worker 自身 UB health 摘要。
  • RPC timeout 不能合成 URMA ERROR 4；只有 URMA operator 或 provider 显式 status 能作为 ERROR 4 归因依据。
  • fallback 默认关闭；开启时也不覆盖迁移/rebalance，不作为 UB health 恢复证据。

7. 可信软件

7.1 安全性 Security

不引入外部通信面；health summary 只携带 worker、状态、epoch、reason、backoff 信息，不携带对象数据。

7.2 韧性 Resilience

通过局部 fail fast、指数退避和 probe 恢复降低持续故障对业务请求和迁移任务的放大影响。

7.3 隐私性 Privacy

不改变数据读写权限和对象内容传输路径；错误状态中不暴露对象 payload。

7.4 可靠性 Reliability

区分 Global Fact 与 Local Observation，避免把局部传输错误误判为对象不存在或 worker 全局下线。

7.5 可用性 Availability

恢复必须由 probe/epoch 证实，避免故障未恢复时继续写入或迁移；fallback 作为显式策略而非默认透明行为。

7.6 安全 Safety

迁移/rebalance 执行前二次检查目标准入，避免把数据迁移到 UB 不可写节点。
