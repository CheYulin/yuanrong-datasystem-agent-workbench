1. 结论摘要

  • Workbench 固定 4 个 Skill（wb-verify / wb-perf-research / wb-html-publish / wb-docs），已删除 ./ops 统一入口，能力下沉到 Skill + 直接脚本路径。
  • 与 Datasystem 分工：产品级流程（ds-dev-loop、ds-pr-flow 等）留在 sibling 仓；Workbench 阶段先验证本仓 Skill，再考虑合并进 datasystem。
  • 与通用 Cursor Superpowers 互补：Superpowers 管「怎么想」（brainstorm / plan / TDD 纪律）；wb-* 管「跑什么命令、在哪台机器、产物放哪」。
  • 竞品对标对象不是 LMCache/Mooncake 存储后端，而是 Agent 编排层：裸 Rules、通用 Skill 市场、单文件 AGENTS.md、已废弃的 ops 路由。

4. 选型决策树

要声称「改完能合」？ ──► wb-verify（smoke/UT/ST + validate_kv_executor）
要挖 perf / 锁 / executor？ ──► wb-perf-research（勿当默认 gate）
要发 yche.me 结论页？ ──► wb-html-publish
要 Markdown 报告 / commit 草稿？ ──► wb-docs
要 PR / 在线文档 / RDMA 专精？ ──► datasystem .skills（后续合并，当前不强制改 DS 仓）

5. 与 LMCache / Mooncake 类「竞品页」的差异

存储后端竞品页（如 LMCache 竞品分析）回答「用什么缓存架构」。本页回答「Agent 用什么可验证工作流」：

  • 结论必须可复现：Skill 表中的脚本路径 + TDD contract。
  • 事实性 datasystem 代码主张需 codegraph 标注 CG-OK；本页流程结论为 CG-NARRATIVE。
  • Draft RFC / 单次 perf 落盘 → workbench rfc/ / results/，不直接进 yche.me。
