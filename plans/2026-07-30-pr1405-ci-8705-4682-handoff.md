### Root Cause 2: `MIGRATION_TARGET` Admission Blocks Normal Recovery/Migration Paths

Representative cases:
- `ObjectClientTest.QueryMetaAndCreateMetaConcurrently`
- `ObjectClientWithTokenTest.QueryMetaAndCreateMetaConcurrently`
- `KVCacheClientTest.TestRemoteGetFromSelfAddressScenarios1`
- `KVClientWriteRocksdbTest.TestNoneModeVoluntaryScaleDown`

- `KVClientWriteRocksdbTest.TestASyncModeVoluntaryScaleDown`
- `RoutingTopologyConvergenceTest.U6ScaleDownRejectsWritesAndConvergesRouting`

Direct log evidence:
- Repeated status family:
  - `kind=MIGRATION_TARGET`
  - `mode=RUNNING`
  - `phase=METADATA`
  - `rejection=RECONCILIATION_INCOMPLETE`
- Downstream symptoms:
  - `Worker is not accepting PublishMeta`
  - `Worker is not accepting MigrateData`
  - `Key not found`
  - `Voluntary scale down did not converge before the test deadline`
  - `topology callback exceeded its deadline`

Relevant source:
- `src/datasystem/worker/runtime/worker_service_admission.cpp`
- `src/datasystem/worker/runtime/worker_runtime_facade.cpp`
- `src/datasystem/worker/runtime/worker_runtime_state.*`
- `src/datasystem/worker/object_cache/master_worker_oc_service_impl.*`
- `src/datasystem/worker/object_cache/service/worker_oc_service_migrate_impl.*`
- `tests/st/client/object_cache/migration_target_admission_test.cpp`
- `tests/st/client/kv_cache/kv_cache_client_test.cpp`

Working hypothesis:
- PR1405 correctly wants ordinary service to reopen at `ServingReady` and migration/primary-sensitive paths to wait for `Complete`.
- The failed CI suggests either:
  - `PublishMeta` is being classified too broadly as `MIGRATION_TARGET`, so normal metadata publication is blocked during background reconciliation; or
  - recovery evidence remains stuck at `METADATA` and never reaches `Complete` in the CI CTest path, so legitimate scale-down/migration never opens.

Important distinction:
- Do not fix this by globally allowing `MigrateData` during incomplete recovery.
- A safe fix should either:
  - make the evidence chain reach `Complete` when it is actually complete; or
  - split admission so only truly primary/migration-sensitive `PublishMeta` paths require `MIGRATION_TARGET`, while ordinary serving paths remain allowed under `ServingReady`.

## Bazel #4682 Root Cause And Fix

Failure:

```text
external/datasystem_sdk_validation/src/datasystem/worker/worker_health_check.cpp failed
worker_health_check.h:18:10: fatal error: datasystem/worker/runtime/worker_runtime_types.h: No such file or directory
```

Root cause:
- `src/datasystem/worker/worker_health_check.h` includes:
  `datasystem/worker/runtime/worker_runtime_types.h`
- It declares:
  `SetTopologyServingAdmission(const worker::WorkerAdmissionGateUpdate &update)`
- The type is provided by Bazel target:
  `//src/datasystem/worker/runtime:worker_runtime_types`
- But `src/datasystem/worker/BUILD.bazel` target `worker_health_check` does not depend on that target.
- Bazel sandboxed external SDK validation only exposes declared headers/deps, so the include fails.
- CMake does not catch this because its source include path is wider and the CMake worker/runtime graph is less strict.

Minimal fix:
- Best boundary fix:
  1. In `worker_health_check.h`, replace the direct runtime include with a forward declaration:

     ```cpp
     namespace worker {
     struct WorkerAdmissionGateUpdate;
     }
     ```

  2. In `worker_health_check.cpp`, include:

     ```cpp
     #include "datasystem/worker/runtime/worker_runtime_types.h"
     ```

  3. In `src/datasystem/worker/BUILD.bazel`, add to `worker_health_check` deps:

     ```python
     "//src/datasystem/worker/runtime:worker_runtime_types",
     ```

- Optional CMake graph hygiene:
  - Add `worker_runtime_types` to `WORKER_HEALTH_CHECK_DEPEND_LIBS`.

Do not:
- Do not add `src/datasystem/worker/runtime/worker_runtime_types.h` to public SDK headers, wheel manifests, or install manifests.
- It is worker runtime internal state/admission protocol, not SDK public API.

Bazel validation:

```bash
bazel build //bazel:source_sdk_client_validation --sandbox_debug
bazel build //bazel:datasystem_wheel
```

If using project wrapper, first inspect branch-specific help:

```bash
bash build.sh -h
```
