关键代码路径

1. Client 侧衰减 — ClientGetRequestTimeout

// client_worker_common_api.h:279
static ClientGetRequestTimeout(int32_t timeout)
{
    const int64_t CLIENT_TIMEOUT_MINUS_MILLISECOND = 1000;
    const double CLIENT_TIMEOUT_DESCEND_FACTOR = 0.9;
    return std::max(
        TimeoutDuration::ScaleTimeoutMs(timeout, CLIENT_TIMEOUT_DESCEND_FACTOR),
        timeout - CLIENT_TIMEOUT_MINUS_MILLISECOND);
}
阈值 SMALL_TIMEOUT_ROUND_THRESHOLD_MS = 10：当 timeout ≤ 10ms 时，用 microsecond 精度计算（+500μs round-up）。当 timeout > 10ms 时，直接 timeout × 0.9。

2. Server 侧初始化 — RouteToRegBackend

inline int64_t WorkerGetRequestTimeout(int32_t timeout)
{
    return std::max(ScaleTimeoutMs(timeout, WORKER_TIMEOUT_DESCEND_FACTOR),
                    timeout - WORKER_TIMEOUT_MINUS_MILLISECOND);  // 0.9× 或 -5000ms
}

ConvertRemainingTimeUsToMs 的 round-up 效应

核心逻辑

// timeout_duration.h:118
static int64_t ConvertRemainingTimeUsToMs(int64_t remainingTimeUs)
{
    if (remainingTimeUs <= 0) {
        return remainingTimeUs / 1000;  // ≤0：直接除以 1000（负数截断向零）
    }
    if (remainingTimeUs > 10 * 1000) {   // > 10ms：直接除以 1000
        return remainingTimeUs / 1000;
    }
    // ≤ 10ms：round-up 到最近的 ms（+500μs 然后除以 1000）
    int64_t roundedTimeMs = (remainingTimeUs + 500) / 1000;  // ceil(x/1000)
    return roundedTimeMs > 0 ? roundedTimeMs : 1;  // 最小返回 1
}

边界值分析

remainingTimeUs (μs)时间 (ms)计算返回 (ms)误差
10.001(1+500)/1000=01+0.999ms
4990.499(499+500)/1000=01+0.501ms
5000.5(500+500)/1000=11+0.5ms
9990.999(999+500)/1000=11+0.001ms
10001.0(1000+500)/1000=110
15001.5(1500+500)/1000=22+0.5ms
-1-0.001-1/1000=00负数直接截断
-1000-1-1000/1000=-1-1返回负数
round-up 的双刃剑：在 deadline 临近时（remainingTimeUs ∈ (0, 10000]），round-up 会多算剩余时间（499μs → 1ms，多算 0.5ms）。但一旦 deadline - currTime 变成负数，remainingTimeUs ≤ 0，则直接返回 ≤0，触发 K_RPC_DEADLINE_EXCEEDED。所以 1ms 的 remaining time 说明 server 端确实收到了请求，但 reqTimeoutDuration 的 deadline 已经非常临近了。

ScaleTimeoutMs 的 micro 精度路径（timeout ≤ 10ms）

// timeout_duration.h:130
static int64_t ScaleTimeoutMs(int64_t timeoutMs, double scaleFactor)
{
    if (timeoutMs <= 0) return timeoutMs;
    if (timeoutMs > 10) return timeoutMs * scaleFactor;  // >10ms: 线性缩放
    // ≤10ms: micro 精度
    int64_t timeoutUs = timeoutMs * 1000 * scaleFactor;
    int64_t scaledTimeoutMs = timeoutUs / 1000;
    if (timeoutUs % 1000 >= 500) ++scaledTimeoutMs;  // round-up if ≥500μs
    return scaledTimeoutMs > 0 ? scaledTimeoutMs : 1;  // 最小 1ms
}
示例：14ms × 0.8 的 micro 路径
输入：timeoutMs = 14，scaleFactor = 0.8
因为 14 > 10，走线性路径：timeoutUs = 14 × 1000 × 0.8 = 11200 μs
scaledTimeoutMs = 11200 / 1000 = 11 ms
11200 % 1000 = 200 < 500，不进位 → 结果 = 11 ms
（若 timeoutMs ≤ 10，则走 micro 精度路径，可能有 +1ms 的 round-up）

RouteToRegBackend Timer Capture 问题

异步分发 + 同步阻塞 = timer 语义失效

关键 Bug：timer 在 lambda 中按值捕获（拷贝了内部状态），但真正的问题在于：

1. thrdPool_->Execute 是异步的，任务进入队列后 RouteToRegBackend 立即返回。
2. backendMgr_->SendMsg 是同步阻塞的（QUE_NO_TIMEOUT = -1），它发生在 RouteToRegBackend 返回之后。
3. 当 SendMsg 阻塞时，lambda 已经在另一个线程中执行了，此时 timer 已经走了 SendMsg 的等待时间。
4. 如果 SendMsg 阻塞了 12ms，那么 elapsed = 12ms，timeout - elapsed = 14 - 12 = 2ms。

可能根因汇总

优先级根因说明
最大嫌疑 SendMsg 阻塞 backendMgr_->SendMsg(workerId, p, QUE_NO_TIMEOUT) 是同步阻塞调用（-1）。当 worker 侧接收队列（ZMQ HWM）满了，SendMsg 会一直阻塞。这个阻塞发生在 timer 创建之后、thrdPool_->Execute 之后。结果：lambda 执行时 elapsed 非常大，timeout - elapsed 变成一个很小的值（甚至负数）。
其次 线程调度延迟 即使没有 SendMsg 阻塞，线程池从 Execute() 到真正调度执行 lambda 之间也有延迟。在高负载下这个延迟可能达到 5~10ms。结合 SendMsg 阻塞，两者叠加会导致 elapsed 非常大。
次要 多层 CHECK_AND_SET_TIMEOUT 衰减 如果请求从 stub 到 server 后，server 端再调用 worker-worker RPC 或 worker-master RPC，每一跳都会经过 CHECK_AND_SET_TIMEOUT → CalcRemainingTime() × 0.8 → WorkerGetRequestTimeout() × 0.9。两跳后：14ms × 0.8 × 0.9 ≈ 10ms，三跳后 ≈ 7ms。链路越长衰减越厉害。
精度损失 elapsed 向下取整 int64_t elapsed = elapsedUs / MS_TO_US 是整数除法，向下取整。如果实际 elapsed = 12.3ms，代码中用 12ms 扣减。但 ConvertRemainingTimeUsToMs 对微小剩余时间的 round-up（499μs → 1ms）并不能弥补这个取整损失。
round-up 掩盖真相 round-up 虚高 当 deadline_ - currTime = 1500μs（1.5ms），ConvertRemainingTimeUsToMs 返回 2ms。但这个 2ms 是"理论值"，实际的 deadline 已经非常近了。加上 CalcRemainingTime() 再做 0.8 缩放，传入下游的 timeout 可能只剩 1~2ms，极易触发超时。
不太可能 clock 不一致 TimeoutDuration 全程使用 std::chrono::steady_clock::now()，是单调时钟，不会因系统时间跳变而受影响。但理论上如果 client 侧和 server 侧使用不同的时钟基准，可能存在不一致。

排查步骤

Step 1：确认 elapsed 大小（Inject Point）

zmq_service.cpp:1055 有一个 inject point，可以注入自定义的 elapsed 值来复现问题：

INJECT_POINT_NO_RETURN("ZmqService::RouteToRegBackend",
                       [&elapsed](int64_t inElapsed) { elapsed = inElapsed; });

在测试中注入 inElapsed = 13000（13ms），观察目的端 remaining time 是否变成 ~1ms。

Bazel 注入方式：
--//src/datasystem/common/rpc/zmq:zmq_service:inject_points=ZmqService::RouteToRegBackend=13000

Step 2：加日志打印 elapsedUs 和 timeout

在 RouteToRegBackend lambda 内部加一行：

LOG(INFO) << FormatString("RouteToRegBackend: timeout=%lld, elapsedUs=%lld, elapsedMs=%lld, remaining=%lld",
                      timeout, elapsedUs, elapsedMs, timeout - elapsedMs);

重点关注：当 timeout - elapsedMs 的值很小（< 5ms）时，后续 RPC 几乎必定超时。

Step 3：确认目的端的 meta.timeout() 原始值

在 WorkerEntryImpl（zmq_service.cpp:675）加日志：

LOG(INFO) << FormatString("WorkerEntryImpl: remainingTime=%lld, meta.timeout=%lld",
                  reqTimeoutDuration.CalcRealRemainingTime(), meta.timeout());

如果 meta.timeout() 本身就已经很小（< 5ms），说明问题在 stub→server 链路；如果 meta.timeout() 还较大但 CalcRealRemainingTime() 很小，说明问题在 server 内部处理耗时。

Step 4：确认是否有多跳 worker RPC

检查请求链路中是否有 worker_master_oc_api.cpp 或 worker_worker_oc_api.cpp 的 CHECK_AND_SET_TIMEOUT 调用。每多一跳都额外乘以 ~0.72（0.8×0.9）。

Step 5：检查 ZMQ HWM 设置

如果 backendMgr_->SendMsg 频繁阻塞，说明 worker 侧接收队列已满。可以查看 ZMQ_SERVER_SNDHWM / ZMQ_SERVER_RCVHWM 等 gflag 配置，以及监控 ZmqServerMsgMgr 的队列长度指标。

Step 6：压测复现

在压测环境中人为制造高负载（多个并发请求占满 worker 队列），观察 elapsedUs 分布。如果 P99 elapsed 超过 5ms，就需要关注 SendMsg 阻塞问题了。

结论

最可能的根因：RouteToRegBackend 的异步分发 + SendMsg 同步阻塞

stub 端剩 14ms，RPC 在 2.5ms 失败，目的端 remaining time 只有 1ms，说明有 ~11.5ms 的时间在 RouteToRegBackend 到 WorkerEntryImpl 之间消失了。


最可能的原因：backendMgr_->SendMsg 的同步阻塞（QUE_NO_TIMEOUT = -1）消耗了大量时间，此时 lambda 已经在另一个线程中执行，导致 timer.ElapsedMicroSecond() 返回了一个很大的值。timeout - elapsed 变成了一个接近 0 的数，server 端的 reqTimeoutDuration 在真正处理请求时就已经快耗尽了。

建议优先排查：ZMQ 队列是否积压、线程池是否饱和、以及 elapsedUs 的实际分布。
