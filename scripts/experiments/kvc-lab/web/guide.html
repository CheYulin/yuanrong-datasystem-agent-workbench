具体步骤与运行记录

基础性能

亲和写入的真实路径

DataSystem 按元数据归属选择写入接入 worker；检查实际请求路由，证明“一跳 RPC”是否成立。

扩展性

中心路径的真实负载

在固定资源预算下增加 workers / clients，结合 Mooncake Master 负载与吞吐曲线判断瓶颈位置。

  • 运行环境固定为 tiantiyun-80c128g。逻辑节点采用不同 loopback 端点与产品 host ID；cgroup 隔离 server / client / monitor 角色，workers 共享服务端总预算，所有节点仍位于同一物理机；不据此声称跨机扩展能力。
  • 服务端与客户端的 cpuset 按物理核选择，互不重叠；40 个物理核保留 2 核监控，两者合计最多 38 核。中心组件只配置子 cgroup 的 cpu.max 核配额，继承服务端 cpuset，并非独占这些物理核；中心限额计入服务端总配额。
  • DataSystem 的 Coordinator 承担集群协调；KV 元数据所有者及查询服务位于 workers 内。测量 Coordinator CPU 不能代替测量所有 worker 元数据路径。Mooncake 的中心是单 Master，增加 workers 在这里指增加 store peers，不是将 Master 元数据分片。
  • 固定总预算实验不能随着 workers 数量增加而默默增加 CPU 或内存。实际 cpuset、cpu.max 和内存限制均以部署回执为准。
  • 两种产品按相同配置顺序重建运行，避免活跃进程互相干扰。DataSystem 使用 Coordinator，关闭本次内存 KV 对比不需要的 RocksDB 与 Stream 功能。
  • 批量 B 表示每次 API 调用的独立 key 数；“API/s”和“keys/s”分开记录。失败、不支持与缺失不能填写为零。

页面操作顺序

  1. 返回控制页，选择预设和资源规格，展开“即将提交的配置”核对输入。
  2. 点击“部署选定拓扑”。确认部署步骤的版本、实际配额与健康检查通过。
  3. 点击“运行所选用例”。后台按产品、规格顺序重建，执行验证、计时与观测。
  4. 在任务列表查看步骤状态、实际耗时与日志。提交结果未知时先刷新原任务，不重复启动。
  5. 结果页切换 PUT / GET / EXIST，按 clients、workers 或逻辑节点查看图表；在完整状态表核对失败与未采集。
  6. 需要停止时点击“停止当前任务”，等待取消与资源回收回执；停止请求成功不等于清理已完成。

05 / READING THE EVIDENCE

如何判断性能差异

  • 一跳 RPC：需要实际亲和 key 与接入 worker 的归属关系、路由和请求证据。只打开配置或吞吐较高，不能证明没有 worker 间转发。
  • 中心瓶颈：吞吐平台、中心配额饱和与配额敏感性共同验证。中心利用率等于采样窗口平均使用核数除以中心配额；节流展示对应窗口的总时长。窗口不同不能直接比较节流总量。若客户端 CPU 饱和、内存不足或传输链路受限，应先排除这些因素。
  • 批量与吞吐：keys/s 和 API/s 表达不同含义。B4096 的单次调用处理 4096 个独立 keys，不能只看 API/s 排名。
  • 有界 PUT 与短窗口：纯 PUT 使用有界 fresh 插入集合，非持续定时 upsert。完整结果保留 put_scope、short_window 和 low_sample_p99；短窗口和低样本 P99 不能只看汇总值，不把缺少资源采样填写成零。
  • 资源口径：服务端 CPU 包含中心组件。内存是服务端 cgroup 采样 memory.current 峰值，包含页缓存；不等同于对象私有内存，也不包含客户端预算。
  • 命中与未命中：EXIST 两类场景分别验证已存在集合和未写入集合。不能把错误码当作未命中，不能把超时记成 0 QPS 的成功点。
  • 重复与范围：每个任务 / 变体的预期轮次（从 0 起）必须唯一、齐全且全部有效，才允许聚合与散点显示；缺轮、重复轮或失败均保留空值。多个任务合并时各自子组都要通过，点的 n 标明实际完整轮次数。不同版本、配额与负载不能混为同一组。
  • 当前边界：本页没有预置性能数字；尚未执行的场景保持空状态。同物理机实验不证明跨机、GPU / RDMA、故障恢复或高可用性。
