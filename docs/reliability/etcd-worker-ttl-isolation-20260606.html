1. 设计立场：为何无法区分网络抖动与真宕机

核心不是「精确判断某台 worker 是否还活着」，而是：

在 etcd 里看不到该 worker 的租约 key → 集群不再把它当作可靠成员。

其他 worker 只能看到 etcd 上 key 被删（租约到期），无法区分是 worker↔etcd 抖动还是进程真挂。若仍按旧元数据路由，容易出现拉不到对象、primary 指向僵尸节点等问题。

因此采用 fail-fast + 事后恢复：

  • 先隔离 / 切主（TIMEOUT 阶段）
  • 再慢清理元数据 / 踢 hash ring（FAILED 阶段）
  • 节点恢复后走 recover / 对账路径

这是典型的 以 CP 的成员视图换可用性：牺牲短暂误判，避免长时间错误路由。

2. 关键参数与两阶段状态机

参数默认值含义
node_timeout_s60setcd 租约 TTL；多久没续上算「失联」
node_dead_timeout_s300s从失联起再过多久判「死亡」；须 > node_timeout_s
heartbeat_interval_ms1000msClient↔Worker 心跳，不是 etcd keepalive 间隔

阶段 A：etcd key DELETE → TIMEOUT（快速止损）

所有 worker watch 到 DELETE 后，HandleNodeRemoveEvent 调用：

NodeTimeoutEvent::NotifyAll(workerAddr, changePrimary=true, removeMeta=false)
  • Master：SetFaultWorker + 切 primary
  • Worker：CheckConnection 对 TIMEOUT 节点返回 K_MASTER_TIMEOUT
  • 暂不 RemoveMetaByWorker

阶段 B：TIMEOUT → FAILED（慢清理）

后台 DemoteTimedOutNodes 周期性执行，当

timeoutStamp > (node_dead_timeout_s - node_timeout_s)

晋升 FAILED 后：

NodeTimeoutEvent::NotifyAll(addr, changePrimary=false, removeMeta=true)
hashRing_->RemoveWorkers(GetFailedWorkers())  // auto_del_dead_node 开启时
时间轴（默认 60s / 300s）： T0 etcd 租约失效，key DELETE T0+~0s 全集群 TIMEOUT：切主、fault 标记、拒绝 RPC T0+~240s FAILED：RemoveMetaByWorker、踢 hash ring

3. KeepAlive 机制（node_timeout_s=1 时 250ms）

3.1 三个时间量

函数node_timeout_s=1含义
etcd Grant TTL1s服务端 1s 内没续租就删 key
GetLeaseRenewIntervalMs()250ms= min(60s, TTL/4)；正常发送节奏
GetLeaseExpiredMs()900ms= max(0.9×TTL, TTL−5s)；单次发送失败的总预算

3.2 正常情况：不是「250ms×4 再等满 1s」

EtcdKeepAlive::Run() 循环：

  1. 发一次 LeaseKeepAlive（gRPC Write + Read）
  2. 成功 → keepAliveTimeoutTimer.Reset()
  3. 若本次耗时 < 250ms，sleep(250 − 耗时)
  4. 重复
理想节奏（node_timeout_s=1）： 0ms KeepAlive 成功，timer 清零 ~250ms KeepAlive 成功 ~500ms KeepAlive 成功 ~750ms KeepAlive 成功 （1s TTL 窗口内多次刷新，key 仍在）

3.3 单次发送失败：250ms 是 wait 步长，不是「只试 4 次」

SendKeepAliveMessage 在 900ms 总预算 内反复 wait_for(250ms)，直到 RPC 就绪或超时。

3.4 外层 LaunchKeepAliveThreads

条件行为
距上次成功 < 900ms 且 keepalive 失败立即重建 stream/租约（无 5s sleep）
距上次成功 ≥ 900ms进入正式故障：可选 fake DELETE、deathTimer、默认 sleep 5s 后重建
etcd 服务端整 1s 没收到续租仍删 key → 其他节点 TIMEOUT
结论（回答「250ms 短 + 失败机制」）：
· 250ms = 正常心跳间隔 + 单次 RPC 等待步长
· 900ms = 本地「这一轮续租已没救」预算
· 1s = etcd 生死线（集群视角）
· 不是「发 4 次 pack 再等满 1s」

4. 网络恢复与 Fake 事件防护

4.1 本机 worker 的额外判断

KeepAlive 失败后，向其他 worker 发 CheckEtcdState，连续 3 次确认 etcd 仍可用 → HandleKeepAliveFailed() 注入 fake DELETE（本机缩容逻辑）。

注意：这不能阻止其他节点在租约到期时收到真实 DELETE 并隔离你。

4.2 恢复路径

  • 重新 Put key，state 从 start/restart 变为 recover
  • ProcessNetworkRecovery → NodeNetworkRecoveryEvent → RemoveFaultWorker
  • Fake remove 若真实节点已存在则忽略（FAKE_NODE_EVENT_VALUE 防护）

5. 元数据清理与重试策略

「清理元数据」分多条路径，重试策略不统一：

路径触发网络失败重试
RemoveMetaByWorkerFAILED / restart否（Master 内存）无专门重试
Master→Worker 异步通知
(DELETE / CACHE_INVALID)		删副本等是有：100ms 轮询 + async 表保留 op
Worker ClearData缩容/故障清理部分有：200ms 定时重试失败 object
OrphanNodeMonitorhash ring 不一致读 etcdetcd 不可用则跳过，下轮再试
SC ClearWorkerMetadataStream 故障本地基本无重试

5.1 Master 异步通知（会重试）

  • ProcessAsyncNotifyOp 每 100ms 扫描 notifyWorkerOpTable_
  • 目标 worker fault → 跳过，日志 "retry next time"
  • RPC 失败 → op 保留，下轮再发
  • 网络恢复 → AsyncNotifyOpToWorker / ProcessAsyncDeleteNotifyOpImpl 补发
  • PushMetaToWorker 等有 RetryOnError（最长约 60s）

5.2 Worker ClearData（会重试）

WorkerOcServiceClearDataFlow：失败 object 进入 ClearDataRetryIds，200ms 后 RetryClearDataAsync，直到失败集为空。

6. 短 TTL 风险与生产建议

node_timeout_s=1 仅适合 ST 压测，不适合生产。
  • gRPC/调度抖动 >250ms 即触发 SendKeepAlive 内层重试
  • 连续失败 ~900ms～1s → 本地故障路径 + etcd 删 key → 集群 TIMEOUT 风暴
  • 每次 TIMEOUT 都切主 + SetFaultWorker
  • 续租频率 = TTL/4 → 1s 时每 250ms 一次，CPU/连接压力大
生产建议：
  • node_timeout_s ≥ 30–60s，明显大于 P99(keepalive RTT + etcd 切换)
  • node_dead_timeout_s 远大于 node_timeout_s（默认 300 vs 60）
  • 缩短感知延迟优先调应用层健康检查，而非把 etcd TTL 压到秒级
